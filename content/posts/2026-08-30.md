> ⏱️째깍악어🐊 선생님 앱에서 **푸시 알림 대상자를 확보**하기 위해 DB와 앰플리튜드로 현황을 분석하고, [Amplitude Guides & Surveys](https://amplitude.com/ko-kr/guides-and-surveys)를 통해 **앱 배포 없이 팝업을 운영**해보았습니다.
> 이 글에서는 분석에서 출발한 의사결정 단계에서부터 맥락별 UX 라이팅, 이벤트·사용자 속성 및 트리거 구성까지 개발 전 단계에서의 작업들을 차례로 정리해 보았습니다. 데이터 기반으로 푸시 유도를 고민하시는 프로덕트 엔지니어분들께 도움이 되기를 바랍니다.

⏱️째깍악어🐊 선생님 앱에서 푸시 알림은 **근처 공고 추천, 채팅, 지원 결과 등 서비스의 핵심 기능을 전달하는 통로**라고 할 수 있습니다. 그런데 데이터와 앰플리튜드를 함께 들여다보니 **푸시 설정을 끄고 있는 선생님**이 생각보다 많더군요. 푸시가 미처 도달하지 못해 우리의 기능이 잘 닿을 수 없는 상황인 것이었습니다.

> 🗣️​ "공고를 너무 늦게 봐서 놓쳤어요."
> 🗣️​ "부모님 채팅을 못 봐서 돌봄 장소가 바뀐지 몰랐어요."

그래서 우리 플랫폼 그룹은 우선 선생님들의 푸시 허용을 목표로 여러 작업들을 수행해보기로 했습니다. 그 중에서 저는 **푸시 허용 팝업을 통해 선생님들의 시스템 알림과 서비스 푸시 허용을 동시에 유도**하는 작업에 착수해 보았습니다.

## 생각보다 많은 선생님들이 시스템 알림을 끄고 있었다.

기존에 시스템 푸시 허용에 관해서는 별도로 추적하고 있던 데이터가 없어, 앰플리튜드에 **시스템 푸시 허용 여부 관련 신규 사용자 속성 `system_notification_permission` 을 심어** 지표를 살펴보았습니다.

| :------------------------------------------------------------------------: |

3일간 이벤트 추이를 확인해보았는데요(비율 확인이 목적이므로 긴 시간으로 잡지 않았습니다), **총 1200명의 선생님 중 약 400명 정도의 선생님들**이 시스템 알림을 꺼두고 계신 상태더군요. **대략 1/3 정도의 선생님들이 시스템 알림을 꺼두고 계신 상태**라는 것인데, 이 수치가 생각보다는 높아 보였습니다. 다른 앱들(⏱️째깍악어🐊 부모님 앱 포함!)과는 다르게 ⏱️째깍악어🐊 선생님 앱에서는 **부모님과의 채팅, 지원 결과** 같은 비홍보성 푸시가 주로 발송되는 상황에서 푸시 허용을 하지 않았다는 것은 **돌봄을 사실상 하지 않겠다**고 선언한 것과 비슷한 상황이라고 해석할 수 밖에 없거든요.

이 푸시 허용 비율은 **활동량이 많은 슈퍼악어 층에서는 많이 달랐는데요**, 시스템 푸시 허용한 사용자 층이 거의 80%에 육박했습니다. 물론 이 중에서도 추천 공고 알림(다소 어노잉할 수 있음)을 허용한 비율은 44%정도까지 떨어지긴 하지만 여러 푸시의 기본이 되는 시스템 푸시를 허용한 선생님들의 비율은 매우 높았습니다. **즉, 실제로 활동하는 선생님일수록 알림을 켜두는 경향이 있고, 아직 깊게 일하지 않았거나 알림 가치를 모르는 선생님들에게는 여전히 푸시 유인이 확실히 있다는 것이었습니다.**

### 푸시 채널은 의미가 있었다.

그렇다면 알림을 켠 사용자에게 채널은 실제로 작동하고 있을까요? 추가적으로 **푸시 도달율(푸시를 실제로 클릭하여 앱 진입) 지표를 확인해 푸시라는 채널 자체가 유의미하다**는 것을 확인했습니다. `utm_source=push`, `utm_content=offer-recommendation`으로 필터링한 **추천 공고 푸시 클릭 후 Page Viewed** 추이를 보면, 일별 **1,000~2,300건** 수준의 유입이 꾸준히 발생하고 있었습니다. 주 1회 정도 눈에 띄는 피크도 보이는데, 추천 공고 푸시가 단순히 발송만 되는 것이 아니라 **실제로 앱 진입으로 이어지고 있다**는 뜻이기도 했습니다.

## Guides를 통해 빠르게 유도 팝업을 띄우다.

DB에서 전환 대상을, 앰플리튜드에서 채널 가치를 확인했지만, **맥락별 팝업을 앱 배포 없이 빠르게 운영**하려면 다른 접근이 필요했습니다. ⏱️째깍악어🐊는 Flutter + WebView 기반의 하이브리드앱이라, 팝업 UI를 네이티브·웹 양쪽에 각각 심고 배포하는 비용이 큽니다.

**Amplitude Guides & Surveys**는 이 지점에서 적합했습니다. 트리거 조건, 노출 빈도, 카피를 대시보드에서 조정할 수 있고, [지난 글](/posts/2026-04-04)에서 Journey 차트와 이벤트 로그를 활용한 경험이 있어 **데이터 기반 운영**으로 자연스럽게 이어갈 수 있었습니다.

### 두 가지 맥락, 두 가지 팝업

OS 알림 권한 다이얼로그는 한 번 거절하면 되돌리기 어렵습니다. 그래서 **맥락에 맞는 soft ask**로 먼저 가치를 설명한 뒤, [기기 알림 켜러 가기] 버튼을 통해 OS 설정으로 유도하는 전략을 택했습니다.

두 팝업은 노출 맥락과 트리거 조건이 다릅니다.

|   팝업    |    노출 맥락     |                        트리거                         |
| :-------: | :--------------: | :---------------------------------------------------: |
|  홈 진입  | 앱 진입(보통 홈) | `system_notification_permission` + `isGranted: false` |
| 지원 완료 |  공고 지원 직후  |   지원 완료 + `system_notification_allowed: false`    |

공통 노출 조건은 **동일 사용자에게 하루 최대 1회**입니다. 알림 유도 자체가 피로를 만들 수 있기 때문에, 빈도를 제한하는 것이 중요했습니다.

홈 진입 팝업은 시스템 알림이 허용되지 않은 사용자에게, 앱 진입 시점에 노출됩니다. 지원 완료 팝업은 공고 지원이라는 **행동이 막 끝난 직후**, 아직 시스템 알림이 꺼져 있는 사용자에게 노출됩니다. 같은 CTA([기기 알림 켜러 가기])를 공유하지만, 사용자가 처한 상황은 꽤 다릅니다.

## 같은 목표, 다른 카피: UX 라이팅을 나눈 이유

두 팝업 모두 **알림을 켜달라**는 같은 목표를 갖지만, 카피 전략은 의도적으로 나눴습니다.

### 홈 진입 — 손실 회피 프레이밍

홈 진입 팝업의 카피는 **"놓치지 마세요!"**로 시작합니다. "선생님께 드리는 혜택, 꼭 맞는 공고를 놓치지 않으려면 기기 알림을 켜주세요."

홈은 탐색과 발견의 공간입니다. 사용자는 아직 특정 행동을 완료하지 않은 상태이고, **놓칠 수 있는 혜택·맞춤 공고**라는 프레이밍이 이 맥락과 자연스럽게 맞닿습니다. 손실 회피(loss aversion) 심리를 활용해도 어색하지 않은 지점이죠.

### 지원 완료 — 손실 회피를 의도적으로 배제

지원 완료 팝업은 다릅니다. **"수업이 확정되면 알려드릴까요?"** "채팅 알림을 허용하고 지원 결과를 바로 받아보세요!"

공고 지원 직후는 결과가 아직 나오지 않은 **불확실한 상태**입니다. 지원 결과는 항상 긍정적으로 느껴지지 않을 수 있습니다. 탈락이나 대기처럼 불확실성 자체가 **불안감**을 야기할 수 있는 순간이기도 하죠.

이때 "놓치면 손해" 같은 프레이밍은 오히려 **압박과 불안을 증폭**시킬 위험이 있습니다. 그래서 지원 완료 팝업에서는 손실 회피를 의도적으로 배제하고, **통제감(control)**을 부여하는 방향으로 풀었습니다.

- **"알려드릴까요?"** — 질문형으로 선택권을 사용자에게 넘깁니다.
- **"지원 결과를 바로 받아보세요"** — 정보 수신을 **능동적 선택**으로 표현합니다.
- **지원 결과의 가치 판단을 서비스가 대신하지 않습니다.** — 좋든 나쁘든, 사용자가 원하면 알림으로 받을 수 있다는 것만 전달합니다.

|             |          홈 진입          |          지원 완료          |
| :---------: | :-----------------------: | :-------------------------: |
| 심리 프레임 | 손실 회피 (놓치지 마세요) |   통제감 (알려드릴까요?)    |
| 사용자 상태 |  탐색 중, 특정 결과 없음  | 행동 완료, 결과 대기·불확실 |
|   카피 톤   |      혜택·기회 강조       |      정보 선택권 부여       |

같은 CTA(알림 켜기)라도 **맥락에 따라 설득 프레임이 달라져야** 합니다. [햅틱 피드백을 적용했던 글](/posts/2026-05-11)에서도 "언제, 왜"를 신중하게 고민했던 것처럼, 이번에도 **어디서, 어떤 상태의 사용자에게, 어떤 말로** 접근할지가 핵심이었습니다.

## 측정 가능하게 만든 이벤트와 사용자 속성

Guides 팝업을 운영하려면 **트리거 조건과 결과 측정**이 모두 가능해야 합니다. 이를 위해 이벤트 로그와 사용자 속성을 정비했습니다.

### 이벤트 로그

|              이벤트              |                   의미                   |                           파라미터                            |
| :------------------------------: | :--------------------------------------: | :-----------------------------------------------------------: |
| `system_notification_permission` | 앱 진입 시 최초 1회, 알림 허용 여부 확인 |                    `isGranted`: true/false                    |
|        `set_notification`        |          푸시 알림 설정 변경 시          | `notification_type`: chat/offer/system, `enabled`: true/false |

`system_notification_permission`은 앱 진입 시 최초 1회 판단하며, Guides 트리거와 `system_notification_allowed` 사용자 속성 갱신에 활용됩니다. `set_notification`은 알림 설정이 실제로 변경될 때 유형별 전환을 추적합니다.

```json
// system_notification_permission
{
  "isGranted": false
}

// set_notification
{
  "notification_type": "offer",
  "enabled": true
}
```

### 사용자 속성

|             속성              |           의미           |     값     |
| :---------------------------: | :----------------------: | :--------: |
| `system_notification_allowed` | OS 시스템 알림 허용 여부 | true/false |
|        `chat_allowed`         |      채팅 푸시 허용      | true/false |
|      `recommend_allowed`      |   공고 추천 푸시 허용    | true/false |

푸시가 채팅과 공고 추천으로 분기되면서, 과거에는 `push_subscribe`, `push_allowed` 같은 단일 속성으로 수집하던 히스토리가 있었습니다. 현재는 **`chat_allowed`와 `recommend_allowed`로 분리**해 수집하고 있으며, 구 속성은 더 이상 사용하지 않습니다.

## Amplitude Guides 설정

두 Guide는 각각 다른 트리거 조건으로 동작합니다.

**홈 진입 Guide**

- 트리거: `system_notification_permission` 이벤트 발생 + `isGranted = false`
- 대상: 시스템 알림이 허용되지 않은 사용자
- 노출 빈도: 동일 사용자 하루 최대 1회

**지원 완료 Guide**

- 트리거: 공고 지원 완료 + `system_notification_allowed = false`
- 대상: 시스템 알림이 허용되지 않은 사용자
- 노출 빈도: 동일 사용자 하루 최대 1회

사용자가 [기기 알림 켜러 가기]를 탭하면 OS 알림 권한 설정으로 이동하고, 이후 설정 변경은 `set_notification` 이벤트로 기록됩니다. Guides의 강점은 **이 트리거 조건과 노출 빈도, 카피를 앱 배포 없이 대시보드에서 조정**할 수 있다는 점입니다.

### 측정 지표

1. **시스템 알림 허용**: `system_notification_allowed = true` 사용자 수(비율) 증가
2. **채팅/공고 알림 허용**: `set_notification` where `notification_type: chat/offer` & `enabled: true` 로그 수, `chat_allowed`·`recommend_allowed` 변화
3. **비즈니스 지표**: 푸시 **전송수**, **도달율** (현재 측정 중)
4. **비교 기간**: 배포 전후 **24시간**, **3일** 두 구간

기대효과는 푸시 알림 대상 교사 **+17,660명**이지만, 앞서 언급했듯 활동 이력 기반으로 좁혀 나갈 수 있습니다. [프리로드 최적화 글](/posts/2026-04-04)에서 Journey 차트만 믿지 않고 `preload-hit`/`preload-requested` 이벤트로 피드백 루프를 구성했던 것처럼, 이번에도 **한 번 배포하고 끝**이 아니라 이벤트 기반으로 지속 관측하는 방향을 택했습니다.

## 마무리하며

이번 작업을 돌아보면, **분석 → 계측 → Guides 운영**이라는 흐름이 꽤 매끄럽게 이어졌다고 느낍니다. DB에서 17,660명이라는 전환 대상을 찾고, 승급 교사 퍼널 붕괴와 연결해 **왜 이 작업이 필요한지**를 설명할 수 있었고, Guides를 통해 **앱 릴리즈 없이 맥락별 팝업**을 빠르게 운영할 수 있었습니다.

개인적으로 가장 인상 깊었던 지점은 **같은 목표(알림 허용)라도 맥락별 카피 전략이 달라야 한다**는 것이었습니다. 홈에서는 손실 회피가 자연스럽지만, 지원 완료 직후에는 오히려 통제감을 주는 것이 맞다는 판단이었죠. FE 개발자로서 코드만 만드는 것이 아니라, **사용자가 어떤 상태에서 이 메시지를 받는지**를 함께 고민해야 한다는 점을 다시금 느꼈습니다.

이벤트와 사용자 속성을 먼저 정비해 둔 덕분에, Guides뿐 아니라 향후 다른 채널의 실험에도 같은 데이터를 재사용할 수 있을 것 같습니다. 기획·마케팅 팀과 트리거 조건과 카피를 함께 조율하며 진행했는데, **좋은 서비스는 혼자 만드는 것이 아니라**는 점을 또다시 확인하는 작업이었습니다 ☺️.
