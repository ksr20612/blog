> 올 상반기, ⏱️째깍악어🐊 라이브러리 모노레포 배포에서 **npm 토큰을 빼고 OIDC Trusted Publishing을 도입**했습니다. 최근 테크 그룹에서 Miasma 이슈를 공유받았고 보안적으로 부족한 지점을 확인했습니다.

며칠 전 테크 그룹 개발자 한 분이 [Miasma](https://www.wiz.io/blog/miasma-supply-chain-attack-targeting-redhat-npm-packages) 사건을 짚어 주셨습니다. 6월 1일 `@redhat-cloud-services` 네임스페이스의 패키지들이 악성 코드가 실린 채로 npm에 배포된 사건이었는데요. 주간 다운로드가 수만 건에 이르는 패키지들이라서 파장이 꽤나 컸던 모양입니다.

중요한 것은 **npm 토큰이 새서 배포된 것이 아니었다**는 점이었습니다. **탈취된 GitHub 계정**으로 짧은 수명의 브랜치에 위조 워크플로우를 올리고, `id-token: write`로 OIDC 토큰을 받아 **Trusted Publishing을 그대로 통과**했습니다. `provenance`도 당연히 유효했습니다. `main`의 브랜치 보호는 깨지지 않았고 정당한 릴리즈 파이프라인도 실행되지 않았던 것이죠.

우리 팀은 올 상반기에 마침 같은 방식-OIDC 배포 방식-을 Changesets 기반의 모노레포에 얹었던 상황이었습니다. 이번 글은 올 상반기의 OIDC 작업과 이 사건을 통해 추가로 도입했던 **GitHub Environment 승인**을 같이 다뤄보려 합니다.

## OIDC를 도입했었는데...

NPM의 [Trusted Publishing](https://docs.npmjs.com/trusted-publishers)은 기존의 액세스 토큰 대신 **GitHub Actions가 발급한 짧은 OIDC 토큰으로 신원을 증명하고 배포**하는 방식입니다. 다만 `changesets/action`에서는 `NPM_TOKEN`이 있으면 해당 토큰을 우선적으로 사용해버리기 때문에 OIDC를 쓰려면 토큰을 비워야 했습니다. 

```yaml
permissions:
  contents: write       # version 커밋, GitHub Release
  id-token: write       # OIDC 토큰 발급
  pull-requests: write  # version packages PR

- name: Upgrade npm (npm >= 11.5.1)
  run: npm install -g npm@11.18.0

- name: Create Release Pull Request or Publish to npm
  uses: changesets/action@63a615b9cd06ba9a3e6d13796c7fbcb080a60a0b # v1.8.0
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    NPM_TOKEN: ''
```

다만 **아직 이러한 방식이 Trusted Publishing에 대응하는 `changesets/action`의 공식적인 방법은 아닌 것**으로 보이는데, 임시 방편으로 해당 방법을 채택했습니다(_추후 공식적인 어나운스가 나오면 교체하려 합니다!_).

액션은 태그 대신 **커밋 SHA로 고정**했습니다. 최근 보안 이슈가 잦기에 안정성이 보장된 특정 커밋 SHA로 고정해둔 것입니다(_실제로 최근 Github에서 보안 강화를 위해 이 방식을 공식적으로 제안하고 있습니다!_). 일반적인 태깅 방식을 사용한다면 의도치 않게 악성 코드가 포함된 로직을 호출할 수도 있으니까요!

## Miasma 공격 앞에서는 OIDC만으로 부족해!

OIDC는 장기간 보관되는 npm 토큰을 없애고 짧은 수명의 인증 토큰을 사용하게 해줍니다. 하지만 **OIDC 토큰을 발급받을 수 있는 GitHub Actions 실행 자체가 공격자에 의해 만들어지는 상황**까지 막아주지는 않습니다.

예를 들어 공격자가 저장소에 워크플로우를 추가하거나 수정할 수 있는 권한을 확보한다면 기존의 정상적인 릴리즈 파이프라인을 거치지 않고도 `id-token: write` 권한을 이용해 OIDC 토큰을 발급받는 실행 경로를 만들 수 있습니다. npm의 Trusted Publishing은 이 토큰이 신뢰된 GitHub 저장소와 워크플로우에서 발급되었는지는 확인할 수 있지만 **그 실행이 실제로 사람이 의도한 정식 릴리즈인지까지 판단하지는 않습니다.**

`provenance` 역시 마찬가지입니다. 패키지가 어떤 GitHub Actions 실행에서 빌드되고 배포되었는지에 대한 출처는 남겨주지만 `refs/heads/oidc-...`와 같은 브랜치에서 실행되었다는 사실 자체가 **“이것은 정식 릴리즈다”라는 의미는 아닐 수 있습니다.**

그렇다면 `changesets/action`을 사용하면 안전할까요? 그렇지도 않은 것 같았습니다. 우리가 의도한 Changesets의 릴리즈 흐름은 `changeset`을 추가하고, `version PR`을 생성·머지한 뒤, **`main`에서 정식 `release.yml`이 실행되는 과정**을 전제로 합니다. 하지만 **공격자가 별도의 워크플로우를 실행할 수 있다**면 이 과정을 통째로 건너뛰고 npm publish까지 도달하는 경로를 충분히 만들 수 있었습니다.

## Required Reviewers의 도입과 함께 고려한 DX

그래서 이번 사태를 보면서 테크 그룹에 개선안을 공유드렸습니다. 결국에는 **실제 npm 배포 직전에 사람의 승인**이 필요하다는 판단이었습니다. 그리고 `GitHub Environment`의 **Required reviewers**로 그 승인을 걸 수 있는 상황으로 보였습니다.

다만 `changesets/action`은 `version PR` 생성과 `publish`를 한 Job에서 처리하기 때문에 `Github Environment`를 Job 전체에 붙이면 배포가 아닌 **version PR을 만들 때도 승인을 받아야 해서 DX가 꽤 나빠질 수 밖에 없었습니다.** 이미 npm 배포 직전에 다른 개발자의 승인이 필요하다는 것조차도 DX 측면에서 나쁜 상황인데 더 나빠진다니...😭​

그래서 Job을 나누기로 결정했습니다. **publish Job에만** `environment: production`을 붙이고, **`id-token: write`도 publish Job에만** 두었습니다. 승인이 필요한 배포 시점을 분리하려는 것이 목적인 셈이었죠.

`production` Environment에는 **Required reviewers**와 **배포 브랜치 제한**을 같이 걸었습니다. npm 패키지 설정의 Trusted Publisher에도 Environment 이름 `production`을 넣었습니다. 워크플로우에 `environment: production`이 없으면 npm이 publish를 거부하고, Environment를 쓰는 워크플로우라도 GitHub가 브랜치와 승인을 검사합니다.
